# 1. 项目定位

Indexing V2 不是一个普通模块，也不是“把 AList 扫一遍”的辅助任务。

它直接决定：

- CloudSite 是否拥有可信的 Folder / Resource 事实；
- Search 是否建立在正确资源之上；
- Catalog、Share、Download 等上层模块是否引用正确资源；
- 重命名和移动后资源关系是否稳定；
- AList / Provider 短暂异常时是否会导致误删；
- 服务崩溃、重启、网络中断后能否恢复；
- 大规模资源下是否能长期运行；
- 管理后台显示的索引状态是否真实；
- 索引损坏时是否存在明确、可审计、可回滚的恢复路径。

因此 V2 后续优化必须独立按一个核心项目管理。

工程优先级统一为：

~~~text
数据正确性
    >
数据安全
    >
故障恢复
    >
一致性
    >
可观测性
    >
性能
    >
便利性
~~~

任何性能优化都不能破坏前五项。

# 2. 当前 V2 事实基线

当前生产 V2 已经是真实执行路径，但仍属于 V2-lite。

当前运行链：

~~~text
Scheduler / Startup / Manual
        ↓
run_indexing_v2_production
        ↓
Providers enabled scan sources
        ↓
AListProviderAdapter
        ↓
Source 串行
        ↓
Root 串行
        ↓
Root 内 BFS 串行
        ↓
内存 CategorySnapshot
        ↓
Reconcile
        ↓
Folders / Resources
        ↓
Search full rebuild
~~~

当前已确认特征：

- Production 已真实使用 V2；
- 不再执行 V1 fallback；
- AList list_path 默认 refresh=false；
- Source 串行；
- Root 串行；
- 目录逐个 await 串行；
- Snapshot 全部存在 Python 内存；
- 扫描中断后不能从断点继续；
- 当前进度主要依赖 system_settings.v2_sync_progress；
- stale running 可能永久阻塞后续同步；
- 第一次扫描和后续扫描没有生命周期区分；
- 每次正常同步都会重新完整遍历 Root；
- Search 每次成功/partial 后完整 rebuild；
- Generic AList 当前不声明原生 delta、cursor、webhook、change journal 能力。

因此当前 V2 的主要问题不是“不可用”，而是：

> 可以工作，但尚未达到核心基础设施应有的可靠性、恢复能力和长期运行成本。

# 3. V2 最终目标

正式目标定义：

> CloudSite Indexing V2 是一个以稳定资源索引为核心，支持首次 Bootstrap、有限并发扫描、持久化断点恢复、稳定 Identity、日常增量维护、滚动一致性校验、低频完整审计和异常重建的索引生命周期系统。

长期运行模型：

~~~text
Bootstrap once
    ↓
Incremental normally
    ↓
Verify continuously
    ↓
Audit occasionally
    ↓
Rebuild only when necessary
~~~

中文解释：

~~~text
首次完整建库
→ 日常只处理变化
→ 持续轻量验证
→ 低频完整审计
→ 只有异常才完整重建
~~~

# 4. 必须长期成立的核心不变量

以下规则属于 V2 的硬约束。

任何 PR 违反其中一条，禁止合并。

## 4.1 不完整扫描不得触发破坏性删除

只要存在：

- pending；
- running；
- retrying；
- failed；
- unknown；
- pagination incomplete；
- Provider 响应异常；
- Root 可访问性不确定；

就不能把“没有扫描到”解释成“Provider 已删除”。

结论：

> Incomplete Scan → No destructive removals.

---

## 4.2 Production Inventory 必须始终代表最后一次可信事实

正式 folders/resources 必须始终保持：

> 最后一次完整、成功、原子提交的可信索引状态。

扫描中间态只能写入 Staging。

禁止扫描一点就逐步覆盖正式索引。

---

## 4.3 Rename / Move 不应改变稳定 Identity

普通重命名和移动应该保持 resource_id / folder_id。

否则会破坏：

- Share；
- Catalog；
- 收藏/历史；
- Download reference；
- 其它未来引用关系。

无法确认 Identity 时必须显式进入 conflict，而不是静默创建一个“看似新的对象”。

---

## 4.4 增量 Cursor 必须在变更成功提交后推进

未来 Provider 支持 Delta 时：

~~~text
load cursor
→ fetch changes
→ apply
→ commit production
→ save next cursor
~~~

禁止先保存 next cursor 再应用变化。

---

## 4.5 Search 是投影，不是事实源

如果：

~~~text
Resources commit success
Search update failed
~~~

必须：

~~~text
Resources 保持成功
Search 标记 dirty
等待 repair/replay
~~~

不能为了 Search 失败回滚已经正确提交的 Resources。

---

## 4.6 Full Scan 只能用于 Bootstrap / Audit / Repair / Rebuild

Ready 状态下不允许 Scheduler 默认反复全量扫描所有 Root。

完整扫描必须从“常规同步方式”降级为“建立或修复事实基线的工具”。

---

## 4.7 Provider 能力必须真实

Generic AList 当前没有可靠 change feed。

因此第一阶段只能使用：

~~~text
Known Changes
+ Rolling Verification
+ Dirty Scope
+ Rare Full Audit
~~~

不能把普通 list 扫描包装成 Delta。

# 6. Root 生命周期设计

每个 Content Root 必须拥有独立索引生命周期。

状态建议：

~~~text
bootstrap_required
bootstrapping
ready
verifying
resume_required
degraded
rebuild_required
disabled
~~~

## bootstrap_required

进入条件：

- 新建 Root；
- Root 没有可信 Baseline；
- Root 配置发生不兼容变化；
- Scan Fingerprint 变化；
- 管理员明确要求 Rebuild；
- Audit 判定现有索引不可安全修复。

## bootstrapping

正在执行完整建库扫描。

## ready

正常稳定状态。

Ready 是 Root 长期运行的默认状态。

## verifying

正在执行滚动一致性验证。

## resume_required

存在未完成但仍有效的持久 Scan Run。

## degraded

正式索引仍可提供服务，但存在：

- Provider 暂时不可达；
- Dirty Scope 持续失败；
- Search dirty；
- Verification 异常；
- 某些变化尚未确认。

## rebuild_required

现有 Baseline 已经无法安全通过局部修复恢复。

# 8. Bootstrap 子项目

Bootstrap 是第一次建立完整事实的过程。

流程：

~~~text
bootstrap_required
        ↓
create scan run
        ↓
bounded async scan
        ↓
durable checkpoints
        ↓
persistent staging snapshot
        ↓
complete gate
        ↓
identity resolve
        ↓
atomic root reconcile
        ↓
search build
        ↓
record baseline
        ↓
ready
~~~

Bootstrap 必须允许：

- 暂停；
- 崩溃；
- 重启；
- 恢复；
- 重新 Reconcile；
- 显式重新开始。

# 9. 有限并发扫描

## 9.1 目标

当前所有目录串行等待 HTTP RTT。

V2 后续改为：

~~~text
asyncio.Queue
+
bounded async workers
~~~

第一版建议：

~~~text
per provider directory concurrency = 8
global scan concurrency = 16
production reconcile concurrency = 1
~~~

参数必须有硬上限。

第一阶段不需要暴露普通 UI 配置。

---

## 9.2 为什么不用传统多线程

扫描瓶颈主要是 HTTP I/O。

当前代码本身已经是 async。

因此优先：

~~~text
async worker
~~~

而不是 ThreadPoolExecutor。

---

## 9.3 为什么不能无限并发

即便 refresh=false：

- AList 缓存可能 miss；
- AList 可能访问底层 Provider；
- Provider 可能有限流；
- CloudSite HTTP 连接池有上限；
- 过量并发放大内存；
- SQLite 写入仍需要控制。

因此必须：

> Bounded concurrency，禁止无上限 gather。

# 10. Durable Scan 子项目

当前最大恢复缺陷：

> CategorySnapshot 全在内存，进程退出后扫描成果全部丢失。

~~~text

index_scan_dirs
index_scan_entries
~~~

这些表是 V2 自有运行态，不复活 Legacy 1.x 表。

# 14. 目录 Checkpoint 事务

扫描目录：

~~~text
/Software/Windows
~~~

AList 返回：

~~~text
Adobe/
Tools/
Chrome.exe
README.txt
~~~

同一个小事务必须：

~~~text
BEGIN

upsert scan entries

insert Adobe as pending dir
insert Tools as pending dir

mark /Software/Windows done

COMMIT
~~~

硬规则：

> 先保存扫描结果与发现的新目录，再把当前目录标记 done。

禁止先 done 再保存 children。

---

# 15. 崩溃恢复

例如：

~~~text
/A        done
/A/B      done
/A/C      running
/A/D      pending
~~~

服务重启后：

~~~text
stale running
→ pending
~~~

结果：

~~~text
/A        done
/A/B      done
/A/C      pending
/A/D      pending
~~~

Workers 只处理 C / D。

已经 done 的目录不重新访问。

---

# 16. Resume 最大有效期

建议第一版：

~~~text
resume_max_age = 60 minutes
~~~

超过有效期：

~~~text
run → expired
staging → cleanup
root → bootstrap_required / restart scan
~~~

避免拼接不同时间跨度过大的 Snapshot。

后续可通过实测调整。

---

# 17. Scan Fingerprint

每次 Scan Run 必须保存配置指纹。

建议输入：

~~~text
connection_id
root_mapping_id
storage_path
adapter_version
scan_schema_version
~~~

任一关键字段发生变化：

~~~text
old run incompatible
~~~

禁止恢复旧 Run。

---

# 18. Complete Gate

这是 V2 最重要的删除安全门。

只有同时满足：

~~~text
pending == 0
running == 0
failed == 0
pagination_complete == true
~~~

才允许：

~~~text
snapshot_complete = true
~~~

只有 complete Snapshot 才允许执行 removal reconcile。

---

# 19. Removal Safety

例如正式索引已有：

~~~text
300,000 resources
~~~

当前 Staging 只有：

~~~text
180,000
~~~

但存在 failed dir。

系统必须：

~~~text
保留正式 300,000
保留 staging
标记 run 可恢复 / failed
禁止删除剩余 120,000
~~~

任何能够在这种情况下产生大规模 removal 的实现都属于 P0 数据安全缺陷。

---

# 20. Atomic Root Reconcile

完整 Staging 完成后：

~~~text
Staging Snapshot
        ↓
Identity Resolution
        ↓
Reconcile
        ↓
one Root production transaction
        ↓
commit
~~~

中间异常：

~~~text
rollback
~~~

正式 Resources 保持上一份完整状态。

如果 Reconcile 自身失败，Staging 应保留，可以直接重试 Reconcile，而不是重新扫描 Root。

---

# 21. Reconcile 变化类型

正式输出至少区分：

~~~text
added
changed
renamed
moved
removed
unchanged
conflict
~~~

后续 Search、Admin、Audit 不应把 rename/move 全部粗暴视为 delete + add。

---

# 22. Identity 子项目

当前路径哈希不能作为最终稳定 Identity 方案。

最终目标：

~~~text
provider stable object identity（如果有）
        ↓
Identity history
        ↓
fingerprint/matching
        ↓
stable resource_id
~~~

需要支持：

- file rename；
- file move；
- folder rename；
- folder move；
- subtree path update。

无法可靠确认时：

~~~text
identity conflict
~~~

不能静默错误匹配。

---

# 23. Identity 硬验收

必须自动化证明：

~~~text
index
→ file rename
→ reindex
→ same resource_id
~~~

~~~text
index
→ file move
→ reindex
→ same resource_id
~~~

~~~text
index
→ folder rename
→ descendants remain valid
~~~

跨 Root move 若明确不支持保持 ID，必须在 Contract 中写清楚，不能行为模糊。



~~~text

~~~

# 26. CloudSite 已知变化

任何由 CloudSite 主动发起且成功完成的：

- 上传；
- 删除；
- 重命名；
- 移动；
- 新建目录；

都应直接产生 ProviderChange。

禁止为了一个已知移动操作重新全量扫描整个 Root。

---

# 27. Provider 原生 Delta

未来 Provider capabilities 同时支持：

~~~text
supports_delta = YES
supports_change_cursor = YES
~~~

才能进入正式 Delta Strategy。

运行：

~~~text
load cursor
→ fetch changes
→ apply changes
→ commit
→ save next cursor
~~~

Cursor 失效：

~~~text
root → degraded
→ verification / audit
→ rebuild if necessary
~~~

---

# 28. Generic AList 的长期策略

当前 Generic AList 没有真实 Delta Feed。

因此采用：

> Hybrid Incremental Mode

~~~text
CloudSite known changes
→ direct incremental apply

unknown external changes
→ rolling verification

verification difference
→ dirty scope

dirty scope
→ targeted scan/reconcile

rare full audit
→ baseline integrity check
~~~

# 30. Dirty Scope 合并规则

已有：

~~~text
/A
~~~

dirty 时：

~~~text
/A/B
/A/B/C
~~~

通常无需重复加入。

相反，如果大量兄弟目录：

~~~text
/A/B1
/A/B2
/A/B3
...
~~~

达到明确阈值后，可以提升为：

~~~text
/A
~~~

但必须有测试，不得无脑扩大扫描范围。

# 31. Directory Fingerprint

每个目录可保存轻量 Fingerprint。

候选输入：

~~~text
child name
is_dir
size
modified
provider object id
~~~

稳定排序后 hash。

Verification：

~~~text
list directory
→ calculate fingerprint
→ compare
~~~

不一致：

~~~text
mark dirty
~~~

---

# 32. Rolling Verification

对于 Generic AList：

~~~text
Scheduler
↓
select directory batch
↓
list_path(refresh=false)
↓
fingerprint compare
↓
verified / dirty
~~~

这是滚动校验，不是 Full Snapshot。

---

# 33. Verification 调度优先级

优先：

- 长期未验证；
- 最近活跃；
- 最近发生变化；
- 之前失败；
- 顶层关键目录；
- 高风险目录。

字段可包括：

~~~text
last_verified_at
last_changed_at
verification_priority
~~~

---

# 34. Verification 的重要限制

禁止假设：

~~~text
父目录未变化
=
整个子树未变化
~~~

不同 Provider 的 modified 传播规则不同。

所以长期必须逐步覆盖实际目录，而不是只检查 Root。

---

# 35. Full Audit

Full Audit 复用：

- Concurrent Scanner；
- Checkpoint；
- Staging Snapshot；
- Complete Gate。

区别：

Bootstrap：

~~~text
建立事实
~~~

Audit：

~~~text
验证事实
~~~

Audit 默认只输出 Diff。

不能默认直接覆盖 Production。

---

# 36. Audit Diff

至少区分：

~~~text
missing_in_provider
missing_in_index
changed
identity_conflict
unexpected_path
duplicate_identity
~~~

只有 Audit 本身完整成功，才允许依据 Diff 做 Repair。

---

# 37. Search Incremental Projection

长期不允许：

~~~text
每次一个小变化
→ DELETE 全部 FTS
→ 全量 INSERT
~~~

目标：

~~~text
IndexChange
↓
Search Projection
~~~

映射：

~~~text
resource_added   → INSERT
resource_updated → UPDATE
resource_renamed → UPDATE
resource_moved   → UPDATE
resource_removed → DELETE
~~~

---

# 38. Search Full Rebuild 的合法场景

只用于：

- Bootstrap；
- Search dirty repair；
- Schema migration；
- Manual rebuild；
- 严重 Projection 损坏。

日常增量不 full rebuild。

---

# 39. Search Dirty Recovery

如果：

~~~text
Resources success
Search update failed
~~~

执行：

~~~text
search_dirty = true
~~~

后续：

~~~text
replay / rebuild projection
~~~

不能破坏 Resources。

---

# 40. Retry 分类

Retryable：

~~~text
timeout
connection reset
429
502
503
temporary provider unavailable
~~~

第一版 backoff 建议：

~~~text
1s
3s
10s
~~~

带少量 jitter。


# 41. stale-running 修复

这是 R0 必须优先解决的问题。

以后 Scan Run 才是事实。

启动恢复：

~~~text

但原 owner/process 不存在
→ interrupted
~~~

目录：

~~~text
running
→ pending
~~~

Root：

~~~text
resume_required
~~~

不再需要人工修改 system_settings 才能重新同步。

# 42. Cancel 语义

Cancel 不能等于“删除一切”。

正确流程：

~~~text
stop workers
↓
preserve checkpoints
↓
preserve staging
↓
run = paused/cancelled
~~~

再次启动：

~~~text
resume
~~~

如果管理员明确选择“重新开始”，才清理 Staging。


失败/暂停：

~~~text
保留 staging
~~~

超过 resume_max_age：


# 52. Crash Recovery 故障注入

必须至少测试：

## 创建 Run 后崩溃

- [ ] malformed response 不误删；
- [ ] anomalous shrink 有 Guard；
- [ ] Reconcile 失败回滚；
- [ ] Search 失败不破坏 Resources；
- [ ] Identity 冲突不静默错误绑定。

# 93. 项目级最终验收 — 恢复

必须满足：

- [ ] process crash 可恢复；
- [ ] service restart 不会永久 running；
- [ ] Scan Run 可续；
- [ ] done dir 不重扫；
- [ ] Staging 可重用；
- [ ] Reconcile 可重试；
- [ ] Search dirty 可恢复；
- [ ] Audit/Repair 有明确恢复路径；
- [ ] 回滚路径经过验证。

# 94. 项目级最终验收 — 性能

- [ ] 无不可控 DB lock；

# 96. 明确禁止的伪完成

出现以下任意情况，不允许声明“V2 优化完成”：

- 只把扫描改成并发，但仍每次定期全量；
- 只保存 last_path，不保存扫描成果；
- Crash 后仍必须全部重扫；
- partial 仍可能 removal；
- rename/move 仍改变 ID；
- Search 每个变化仍 full rebuild；
- stale running 仍需手工改库；
- Provider 失败被解释为空目录；
- E2E 靠 skip 掩盖数据缺失；
- 性能没有 baseline；
- 只有 CI green，没有 fault injection；
- Admin 显示不存在的百分比；
- 多 Root / 多 Connection 仍可能互相覆盖；
- Audit 一边扫描一边直接破坏 Production；
- 为了“完整架构”强行引入默认部署无法消费的 Worker 系统。

# 101. 最终工程原则

V2 后续优化不能只围绕“扫描更快”。

真正目标是建立：

> 高可靠、可恢复、增量优先、故障安全、Identity 稳定、可验证、可审计、可长期运行的资源索引系统。

各能力的意义：

~~~text
并发扫描       → 性能
Checkpoint     → 中断恢复
Persistent Staging → 事实隔离
Complete Gate  → 删除安全
Atomic Reconcile → 生产一致性
Identity       → 稳定引用
Root Lifecycle → 首次/后续区分
Incremental    → 日常低成本
Dirty Scope    → 局部修复
Verification   → 弥补 AList 无 Delta
Search Delta   → 查询投影低成本
Audit          → 长期一致性
Guard Rails    → 极端异常防误删
~~~

最终裁决原则：

> 如果“更快”和“更安全”冲突，优先安全。

> 如果“更复杂”和“可恢复”冲突，优先可恢复。

> 如果“理论架构完整”和“当前部署可靠”冲突，优先当前部署可靠。

> 如果测试无法证明不会误删，就视为尚未完成。

这四条是 CloudSite Indexing V2 后续开发的最高工程原则。
