# 同步安全与第 49 次异常审计

## 已确认事实

目标部署 `index.db` 的第 49 次同步发生于 `2026-08-28 08:25`：

- 扫描结果：113 个目录、166 个资源，共 279 个对象。
- 变化记录：新增 279、缺失 279、修改 0。
- 第 47、48、50、51 次扫描的对象总数相同；第 47、50、51 次均为零增删。
- 新路径以 `/115网盘/CloudSite/软件/...` 开头，旧路径以 `/软件/...` 开头。
- 当时没有 `sync_root_results` 明细，无法在提交前按内容根阻断。

## 结论

这不是 279 个真实对象同时新增、另 279 个真实对象同时删除。扫描对象数量和相对目录结构未变，变化来自路径基线整体增加 `/115网盘/CloudSite` 前缀，旧版路径派生 ID 因而把同一批对象识别为全新对象。

路径基线切换可能来自 AList 用户 base path、内容根配置或扫描规范化逻辑变化。现有证据足以确认“身份整体重建”的机制，但不足以单独断言是哪一个操作触发了 base path 切换。

## v0.1.3 处理

1. 每个内容根完整扫描后，先计算候选新增、候选缺失和原活跃总量。
2. 达到大规模变化阈值时，整个内容根零写入：不新增、不更新、不改变缺失状态。
3. `sync_root_results` 保存扫描量、候选新增、候选缺失和保护原因，便于后台审计。
4. 普通小规模缺失先标记 `suspected_missing`；第二次独立完整扫描仍缺失才转为 `missing`。
5. 候选对象在第二次扫描前重新出现时恢复 `active`，缺失次数和候选时间清零。

## 历史合集引用

第 49 次同步发生在 v0.1.3 保护逻辑上线前。`state.db` 中“优秀作品”合集的 4 条关联仍指向旧 missing 资源 ID，因此旧接口曾出现列表计数为 4、详情加载为 0 的不一致。

只读联表核对确认，这 4 条旧路径都能在增加 `/115网盘/CloudSite` 前缀后唯一匹配到 4 个 active 资源。v0.1.3 已先把合集计数改为只统计 active 资源；是否更新这 4 条历史关联属于独立数据迁移，应在备份后明确执行并保留反向映射。

## 验收场景

- 同一路径连续两次缺失：第一次不产生 removed，第二次产生一次 removed。
- 第一次缺失、第二次重新出现：对象恢复 active，不产生 removed。
- 模拟 279 个路径统一增加前缀：同步状态为 `suspicious_churn`，索引对象及路径零变化，根结果记录候选 `+279/-279`。
- 内容根扫描中途失败：旧索引零变化，不推进缺失确认次数。
